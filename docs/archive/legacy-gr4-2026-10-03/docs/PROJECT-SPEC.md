# 墨水屏黑白相框 — 产品需求文档（PRD v2.0）

> 2026-10-01 展示需求补充（用户最新指令，优先于下文旧 Fit 默认）：图片全屏展示，根据屏幕尺寸等比放大并居中裁切，不拉伸、不新增纸边。旧 v2.0 正文保留作需求历史。三张带白框样片仅在展示副本显式去除内置白框；相机原片不改动。缓存布局须区分 Cover 与旧 Fit，不能复用旧缓存冒充全屏。

> 产品形态：基于 MindReset Read Pico（“小纸”）的理光 GR 系列黑白影像展示终端  
> 当前首发相机：RICOH GR IV  
> 文档状态：产品定义 + Demo Gate + MVP 需求  
> 版本：v2.0  
> 日期：2026-09-29

## 0. 产品结论

这个产品不应被定义为“一个能自动下载照片的电子相框”，而应被定义为：

> **一台把 GR 的拍摄结果自然带回现实空间的电子纸影像终端。**

核心体验不是“管理照片”，而是：

> **拍完即落纸；平时只做「留下 / 放下」两个决定。**

产品必须坚持四个原则：

1. **不依赖手机维持日常使用链路**：完成首次配置后，日常拍摄、同步、展示不需要手机 App 或云服务。
2. **不碰相机原片**：V1 相框只读取和管理自己的展示副本，不提供从相框删除 GR IV 原片的能力。
3. **电子纸不是低配 LCD**：避免秒级轮播、持续动画和高频刷新，利用“像纸一样停在那里”的特性设计体验。
4. **协议能力先验证、再承诺**：GR IV 的 Transfer Reservation 是产品入口，但“第三方设备能否直接识别预约状态并完成下载”必须经过真机验证，不在协议验证前写成既定能力。

# 1. 产品洞察与机会

## 1.1 用户问题

摄影用户面临的核心问题不是“缺少存照片的地方”，而是：

- 拍摄完成后，大量值得被看见的照片进入手机、电脑或 NAS，随后沉没；
- 手机相册是“管理工具”，不是“长期展示媒介”；
- 彩色 LCD 数码相框亮、动、持续发光，容易成为环境中的又一块屏幕；
- 云相框和 App 相框依赖账号、网络、手机权限及服务持续运营，摄影设备与展示设备之间链路过长；
- 对 GR 用户而言，“拍摄 → 回看 → 手机导入 → 选图 → 上传相框”操作成本过高，难形成长期习惯。

## 1.2 核心洞察

Read Pico 的 4.7 英寸电子纸、原生 16 灰阶、低功耗静态显示，与 GR 系列强调随身、街拍、即时观察的使用方式天然匹配。

用户真正需要的不是另一套“照片管理系统”，而是缩短下面这条链路：

```text
拍摄
  ↓
表达“这张我想带回来”
  ↓
照片自动进入现实空间
  ↓
偶尔做一个很轻的判断：留下 / 放下
```

## 1.3 产品机会

传统数码相框通常竞争的是：

```text
屏幕更大 / 彩色 / 云相册 / 家庭共享 / 视频
```

本产品应该反向竞争：

```text
更安静
更像纸
更少操作
更贴近相机
不依赖手机
不过度打扰
```

产品价值不是“显示能力更多”，而是**照片进入生活空间的阻力更小**。

# 2. 产品定位

## 2.1 产品名称

工作名称：**墨水屏黑白相框**

后续品牌命名建议单独进行，不在本 PRD 中确定最终商品名。

## 2.2 一句话定位

> **为 RICOH GR 用户打造的电子纸影像终端：拍完自动出现，不用手机搬照片。**

## 2.3 核心体验语

> **拍完即落纸。**

## 2.4 产品关键词

```text
GR
电子纸
黑白
安静
本地
自动同步
留下 / 放下
照片回到生活空间
```

## 2.5 首发场景

Read Pico 屏幕为 4.7 英寸，机身约 117.5 × 66.2 mm，因此首发应优先定义为**近距离个人影像摆件**，而不是传统客厅大尺寸墙面相框。

优先场景：

- 办公桌；
- 床头；
- 书架；
- 工作台；
- 冰箱 / 磁吸底座；
- 摄影桌面展示；
- 小型桌面相框支架。

“拍完即上墙”可以保留为传播概念，但产品体验文案建议改成“拍完即落纸 / 拍完即上框”。

# 3. 目标用户

## 3.1 核心用户

使用 RICOH GR IV，并满足以下特征中的多个：

- 喜欢街头摄影、日常记录、人文摄影；
- 偏爱黑白、胶片感或低干扰展示方式；
- 拍摄频率较高，但很少系统整理手机相册；
- 希望优秀照片被长期看到，而不是沉在存储中；
- 不希望再维护一个必须持续登录、联网、上传的云端相框 App。

## 3.2 不应过度限制为“只拍黑白的人”

输入照片可以是彩色 JPEG，也可以是相机内已经生成的黑白 JPEG。

产品统一输出为 16 灰阶电子纸效果。

因此 V1 的非目标应定义为：

> **不支持彩色显示。**

而不是：

> 不支持彩色照片。

否则会人为缩小用户范围，并增加用户在相机端提前切换黑白模式的负担。

# 5. 产品承诺与边界

## 5.1 对用户的目标承诺

完成首次配置后：

> **从 GR IV 设置传输预约，到照片出现在相框中，日常链路不需要手机和云端。**

注意：这是产品目标体验，正式作为商品承诺前，必须先通过“GR IV 协议 Demo Gate”。

## 5.2 明确不承诺

V1 不提供：

- 从相框删除 GR IV 原片；
- RAW 显示 / RAW 开发；
- 云端同步；
- 互联网远程访问；
- 视频播放；
- 彩色显示；
- 社交分享；
- AI 自动审美评分；
- 秒级相册轮播；
- 手机 App。

# 7. 产品设计原则

## 7.1 “照片优先，UI 隐身”

默认状态下整块屏幕应该像一张照片或一张打印纸，而不是一个带按钮的电子设备。

只有用户主动交互时才出现菜单、状态和控制信息。

## 7.2 “显示”而不是“轮播”

V1 不使用传统数码相框的高频 Slideshow 心智。

推荐使用：

- “换片”；
- “下一张”；
- “展示间隔”；
- “今日照片”；

不推荐使用：

- “播放”；
- “轮播动画”；
- “幻灯片速度”。

默认换片周期应以分钟或小时为单位，而不是秒。

## 7.3 “留下 / 放下”代替“喜欢 / 删除”

照片行为采用情绪负担更低的语言：

```text
留下
放下
```

其中：

- **留下**：明确希望这张照片长期出现在相框中；
- **放下**：这张照片以后不主动展示，但不影响 GR IV 原片。

## 7.4 不把不可逆操作放在相框主交互中

相框可以删除自己的本地展示副本，但不能直接删除相机原片。

本地删除也必须和“放下”区分。

# 8. 核心用户旅程

## 8.1 首次配置

```text
开机
 ↓
检查 microSD
 ↓
进入“连接相机”
 ↓
发现 GR IV
 ↓
建立配对 / 认证
 ↓
提示用户在 GR IV 开启：
- 2.4 GHz Wi-Fi
- Automatic Image Transfer（如使用）
- Auto Resize Transfer
 ↓
拍一张测试照片
 ↓
设置传输预约
 ↓
相框收到照片
 ↓
显示测试照片
 ↓
配置完成
```

首次配置可以需要用户操作相机菜单，但目标是不要求安装手机 App。

## 8.2 日常同步

理想路径：

```text
用户拍照
 ↓
GR IV 自动预约 / 用户手动预约
 ↓
相框感知有待同步照片
 ↓
建立相机 Wi-Fi
 ↓
读取待同步 JPEG
 ↓
写入 microSD 临时区
 ↓
读取 EXIF
 ↓
生成 1216×684 16 灰阶展示版本
 ↓
原 JPEG 可保留或按存储策略清理
 ↓
最新照片优先显示
```

## 8.3 日常查看

```text
相框静态展示
 ↓
到设定时间自动换片
或
用户左 / 右滑动切换
```

## 8.4 用户判断

```text
长按当前照片
 ↓
[ 留下 ]  [ 放下 ]  [ 更多 ]
```

“更多”中包含：

- 照片信息；
- 从本机删除副本；
- 重新渲染 / 重新下载（如源仍可访问）；
- 取消。

不出现“删除相机原片”。

# 9. GR IV 协议 Demo Gate

这是项目能否成立的第一优先级验证，不应与 UI 开发并行消耗大量资源。

## 9.1 官方行为已经确认的部分

GR IV 支持：

- 相机端 Transfer Reservation；
- Automatic Image Transfer；
- Auto Resize Transfer；
- 使用 Bluetooth 维持普通连接；
- 图像传输时切换到 Wi-Fi；
- GR IV 可在 2.4 GHz / 5 GHz Wi-Fi 间配置。

官方 GR WORLD 的行为可以证明“预约照片存在可识别的状态”，但**不能直接证明第三方 ESP32 设备能通过公开接口读取这个预约状态**。

## 9.2 当前必须验证的技术问题

### Gate A — 相框是否能独立与 GR IV 建立必要的身份关系

必须验证：

- BLE 发现；
- 配对 / 绑定；
- 相机关闭后的重新发现；
- 是否能触发或等待 Wi-Fi 可用；
- 相机重启后的恢复。

### Gate B — 相框是否能访问相机照片列表

必须验证：

- 可列出文件；
- 可得到文件名 / 文件大小 / 拍摄时间；
- 可下载 JPEG；
- 下载中断后可安全重试。

### Gate C — 是否能识别“传输预约”

必须回答：

> 第三方设备能否区分“全部照片”和“已经设置 Transfer Reservation 的照片”？

如果不能，则不能宣称“通过 Transfer Reservation 精准同步”。

### Gate D — 是否能正确回写传输状态

需要验证：

- 下载完成后，GR IV 是否认为该照片已传输；
- 是否必须调用某个状态更新接口；
- 如果不回写，GR WORLD 与相框是否会产生状态冲突；
- 重启后会不会重复同步。

## 9.3 产品兜底路径

协议能力按优先级定义为：

```text
A. 精准读取 Transfer Reservation 队列
   ↓ 不可行
B. 读取“未传输”状态并增量同步
   ↓ 不可行
C. 使用文件时间 / 文件号 + 本地同步游标同步新增照片
   ↓
D. 用户在相框上手动点“同步最新”
```

A 是目标体验。

D 是 Demo 与工程测试的最低兜底，不应成为最终核心卖点。

## 9.4 协议文档要求

在 Gate 完成前，PRD 不指定 FTP、PTP-IP、HTTP 或其他传输协议。

实际协议必须以：

- 真机抓包；
- GR WORLD 行为；
- 已验证的相机接口；

为依据确定。

# 10. 照片数据模型与生命周期

## 10.1 三层数据必须分离

```text
GR IV 原片
   ↓ 只读
导入 JPEG
   ↓
相框展示副本
```

### GR IV 原片

相框 V1 永不主动删除。

### 导入 JPEG

用于：

- 重渲染；
- EXIF 读取；
- 本地 Web 管理；

可以根据存储策略保留或清理。

### 展示副本

建议预生成与屏幕匹配的 16 灰阶数据，以换片时快速显示。

## 10.2 照片状态

建议数据状态：

```text
NEW        新同步，未做判断
NORMAL     正常参与展示
KEPT       用户“留下”
PUT_AWAY   用户“放下”，不参与自动展示
TRASHED    本机文件已删除，但保留防重同步记录
```

## 10.3 “放下”不是删除

选择“放下”后：

- 当前画面立即切换到下一张；
- 该照片不再进入普通自动展示；
- GR IV 原片保持不变；
- 本地元数据保留；
- 默认保留撤销入口；
- 本地存储紧张时，可以优先清理 PUT_AWAY 对应的 JPEG 缓存。

## 10.4 Tombstone（防重复同步记录）

即使用户删除了本机副本，也必须保留轻量记录：

```text
camera_id
source_path / file_number
capture_time
file_size
optional_hash
local_state
```

目的：

> 避免已经“放下”或删除的照片在下一次连接 GR IV 时重新回来。

这是“永久过滤”真正应该落到的数据层机制。

## 10.5 去重策略

优先级建议：

```text
相机身份 + 文件路径 / 文件号
        ↓
拍摄时间 + 文件大小
        ↓
必要时计算部分 Hash
```

不要只依赖文件名，因为相机可能在文件编号循环或介质更换后出现同名文件。

# 11. 照片交互设计

## 11.1 默认展示态

正常状态不显示按钮。

屏幕只展示照片或“照片 + 纸边”。

## 11.2 基础操作

触屏：

```text
左滑：下一张
右滑：上一张
轻点：显示 / 隐藏照片信息
长按：照片操作
```

三个触摸键：

```text
KEY1：上一张
KEY2：当前照片操作
KEY3：下一张
```

按键和触控提供相同能力，以降低学习成本。

## 11.3 长按操作菜单

```text
┌──────────────────┐
│      ♡ 留下       │
│      ○ 放下       │
│      ⋯ 更多       │
└──────────────────┘
```

## 11.4 放下后的反馈

用户选择“放下”：

```text
当前照片淡出 / 刷走
 ↓
下一张出现
 ↓
角落短暂显示：
“已放下 · 撤销”
```

撤销窗口建议通过交互测试确定，不在 PRD 固定为某个秒数。

## 11.5 “留下”的产品含义

V1：

- 加入 KEPT；
- 提高自动展示优先级；
- 不会被自动空间清理策略删除展示副本。

P1：

- 支持“只看留下”；
- 支持按时间生成“留下的照片”集合；
- 支持 Web UI 批量导出。

# 12. 显示模式

## 12.1 默认：纸边模式

GR IV 常见照片比例为 3:2，而 Read Pico 屏幕比例更宽。

默认不应强制裁掉摄影构图。

推荐：

```text
┌────────────────────────────┐
│                            │
│     ┌────────────────┐     │
│     │                │     │
│     │     照片       │     │
│     │                │     │
│     └────────────────┘     │
│          留白区域           │
└────────────────────────────┘
```

这会自然形成类似相纸 / 暗房放大照片的视觉语言。

## 12.2 P1：信息相纸模式

可在留白区展示：

```text
2026.09.29  17:42
f/5.6   1/250   ISO 800
RICOH GR IV
```

如 EXIF 中存在 GPS，可提供地点信息；没有则不显示，不依赖云端反查地名。

## 12.3 P1：满屏模式

允许用户选择 Fill，但必须明确会裁切画面。

默认仍应为 Fit / 完整构图优先。

## 12.4 横竖屏

P1 使用加速度计实现：

- 自动识别设备横放 / 竖放；
- 重新选择适合的照片版式；
- 避免设备轻微晃动导致频繁重排。

# 13. 16 灰阶渲染策略

## 13.1 产品层要求

产品对用户只暴露一个概念：

> **固定的“小纸黑白影像风格”。**

用户不需要调整：

- Gamma；
- 抖动参数；
- 黑位；
- 白位；
- 对比度；
- 锐化。

## 13.2 不在 PRD 过早锁死 Floyd-Steinberg

Read Pico 本身原生支持 16 灰阶，因此是否使用 Floyd-Steinberg、蓝噪声或单纯 16 级量化，应通过真实屏幕样片决定。

V1 渲染 pipeline 建议定义为：

```text
JPEG 解码
 ↓
EXIF Orientation
 ↓
缩放 / Fit
 ↓
亮度 / Gamma 映射
 ↓
局部对比度与轻量锐化
 ↓
16 灰阶量化
 ↓
可选 Dither
 ↓
生成屏幕展示缓存
```

算法可以调整，但同一固件版本中对所有图片使用一致 profile。

## 13.3 输入格式

P0：

- JPEG；
- GR IV 的 Auto Resize Transfer / XS JPEG 优先。

非目标：

- RAW / DNG 解码；
- 视频；
- HEIF。

如果用户使用 RAW+JPEG，则同步 JPEG。

如果用户只拍 RAW，V1 应明确提示无法显示，而不是在 ESP32 上实现完整 RAW 开发。

# 14. 同步策略

## 14.1 Auto Resize 应成为推荐配置

GR IV 的 XS JPEG 最大边约 1920 px，已经高于 Read Pico 1216 × 684 的实际显示需求。

因此首发推荐链路：

```text
GR IV Transfer Reservation
 +
Auto Resize Transfer ON
 ↓
XS JPEG
 ↓
Read Pico
```

收益：

- 更少 Wi-Fi 传输时间；
- 更少功耗；
- 更低 PSRAM 压力；
- 更快 JPEG 解码；
- 更低 microSD 写入量；
- 减少同步失败窗口。

## 14.2 同步触发

理想状态：

- BLE 低功耗监听 / 连接；
- 发现预约后才打开高功耗 Wi-Fi；
- 同步完成后退出 Wi-Fi；
- 回到低功耗展示态。

如果无法通过 BLE 获知队列，则按 Demo Gate 结果调整。

## 14.3 多张照片连续同步

不能“每收到一张就立刻刷新一次屏幕”。

推荐：

```text
短时间内只收到 1 张
→ 同步完成后立即显示

短时间连续收到 N 张
→ 后台全部同步
→ 等本轮同步稳定后，只刷新显示最后一张
→ 其他照片进入 NEW
```

这样避免连续拍摄时墨水屏频繁全刷。

## 14.4 同步失败

失败不应打断相框当前展示。

UI 只在必要时展示轻量状态：

```text
同步未完成
稍后重试
```

而不是弹出模态错误页面覆盖照片。

## 16.1 核心原则

```text
  ↓

  ↓
EPD_REFRESH
  ↓
```


这比持续亮屏式设备更符合电子纸产品逻辑。

# 21. 异常与恢复要求

| 场景 | 产品行为 |
| --- | --- |
| GR IV 不在附近 | 保持当前照片，不弹错；稍后再尝试 |
| 相机关闭 | 不影响展示 |
| 相机正在拍摄 | 不强制抢占或反复重连 |
| Wi-Fi 建立失败 | 本轮同步延期，当前照片继续展示 |
| 下载中断 | 临时文件不进入正式照片库；下次重试 |
| 同一照片重复发现 | 本地索引判断已同步，不重复导入 |
| 已放下照片再次出现在相机中 | Tombstone 阻止重新进入展示库 |
| microSD 被拔出 | 停止写入并提示；不继续向无效路径写文件 |
| microSD 插回 | 用户确认 / 自动校验后恢复 |
| 设备断电 | 屏幕保留最后画面；下次启动恢复索引与待同步状态 |
| 渲染失败 | 保留原 JPEG，记录失败，不产生损坏展示副本 |
| 存储不足 | 优先清理可重建缓存；不自动删除 KEPT 源 JPEG，除非用户配置允许 |

## 22.1 数据原则

```text
照片默认只存在：
GR IV + 用户自己的 microSD / 相框
```

不上传官方云端，也不要求产品账号。

## 22.2 Web UI

Web 管理只允许：

- 设备 AP；或
- 用户信任的局域网。

## 22.3 文案边界

可以宣传：

> 不依赖云端，照片保存在你的设备里。

不要在没有存储加密前宣传：

> 照片经过加密，任何人都无法读取。

microSD 被物理取出后仍属于可直接访问介质。

# 23. MVP 成功指标

产品 Demo 不应只验证“能显示照片”，而应验证完整闭环。

## 23.1 技术成功指标

建议 Demo 验收至少包含：

- 连续 50 次单张预约同步，不出现重复照片；
- 连续拍摄场景可以完整同步，屏幕不会因每张到达而连续全刷；
- Wi-Fi 中途断开后可以重新同步；
- 相机重启后可以恢复；
- 相框重启后不会把历史照片全部重复导入；
- “放下”状态重启后仍然有效；
- 已放下照片不会因为再次扫描相机而重新出现；
- 相框任何操作都不会删除 GR IV 原片。

## 23.2 体验成功指标

用户完成首次配置后：

```text
拍摄
→ 预约
→ 不碰手机
→ 相框出现照片
```

必须成为稳定、可重复的体验，而不是偶发 Demo。

## 23.3 性能目标

在协议路径验证后再正式冻结数值。

建议工程目标：

- 相机 Wi-Fi 已可用后，单张 XS JPEG 同步到完成显示的 P95 ≤ 30 秒；
- 用户手动换片操作到画面稳定完成，应保持在电子纸用户可接受范围；
- 同步失败不能阻塞本地浏览。

## 23.4 功耗目标

在完成真实功耗测试前不对外承诺续航天数。

内部应建立标准测试模型，例如：

```text
每天同步 20 张 XS JPEG
每天自动换片 24 次
其余时间低功耗待机
```

记录：

- BLE 待机功耗；
- Wi-Fi 建链平均耗时；
- 单张下载能耗；
- 16 灰阶全屏刷新能耗；
- microSD 写入能耗；
- 真实单次充电使用天数。

# 26. 关键产品决策

## 决策 1：相框不管理相机原片

**结论：确定。**

V1 永远只读 GR IV。

理由：

- 降低误删风险；
- 降低 RAW+JPEG 语义复杂度；
- 降低用户心理负担；
- 降低协议实现风险。

## 决策 2：删除改成“放下”

**结论：确定。**

“放下”属于展示状态，不是文件操作。

## 决策 3：RAW 不进入 V1

**结论：确定。**

相框最终只有 1216 × 684、16 灰阶，RAW 解码成本远高于产品收益。

## 决策 4：microSD 是照片库，不是可选附件

**结论：建议确定。**

16 MB Flash 不适合作为正式照片库。

## 决策 5：固定视觉风格，底层算法可迭代

**结论：确定。**

用户不可调参数，但团队可以持续调优渲染 pipeline。

## 决策 6：自动换片不能高频

**结论：确定。**

电子纸应该像照片，不应该模拟 LCD Slideshow。

# 27. 待验证问题清单

在进入 MVP 开发前必须回答：

### GR IV

- 第三方是否可读取 Transfer Reservation 状态？
- 下载完成后如何标记已传输？
- 是否存在与 GR WORLD 相同的认证 / session 机制？
- BLE 是否可以触发 GR IV Wi-Fi？
- 相机关闭时能否由 BLE 唤醒并进入传输？
- GR WORLD 与相框交替使用时是否冲突？
- WPA2 / WPA3 设置对 ESP32-S3 兼容性如何？

### Read Pico

- 单张 XS JPEG 峰值解码内存；
- JPEG → 1216×684 灰阶处理耗时；
- 16 灰阶刷新真实耗时；
- 连续 GC16 刷新残影情况；
- 不同环境温度下刷新表现；
- microSD 长时间写入可靠性；
- Wi-Fi 建链平均功耗；
- BLE + 深睡策略是否能满足续航目标。

### 用户体验

- 用户是否理解 Transfer Reservation？
- 用户是否愿意在首次设置时开启 Auto Resize？
- “留下 / 放下”是否比“喜欢 / 删除”更自然？
- 默认是完整构图还是满屏裁切更受欢迎？
- 新照片到达后应该立即抢占当前照片，还是等当前展示周期结束？
- 用户一天拍很多张时，哪些照片应该自动出现？

| Floyd-Steinberg 固定 | 固定产品风格、算法待样片验证 | 原生 16 灰阶不应过早绑定某种抖动算法 |
| “轮播” | “换片 / 展示” | 更符合电子纸产品心智 |
| “不喜欢 / 永久过滤” | “放下 + Tombstone + 可恢复” | 降低心理负担，同时真正解决重复导入 |
| USB / SD P0 | microSD P0，Web P1，USB TBD | USB-C 不等于已具备文件导入能力 |
| P2 喜欢 | P1 “留下” | 与“放下”构成产品核心交互 |

| 删除边界模糊 | 相机只读，本机副本可删 | 保护原片、降低风险 |
| 无同步状态模型 | NEW / NORMAL / KEPT / PUT_AWAY / TRASHED | 支撑长期使用与可靠同步 |

# 30. 参考依据

本 PRD 的硬件基线来自 MindReset Read Pico 官方文档与 `MindReset/read_pico_firmware` 当前公开仓库。

已确认的硬件与固件能力包括：

- ESP32-S3；
- 16 MB Flash；
- 8 MB PSRAM；
- 4.7 英寸、1216 × 684、原生 16 灰阶电子纸；
- 双点触控；
- 三个触摸按键；
- microSD；
- 2.4 GHz Wi-Fi；
- BLE 5.0；
- 2050 mAh 可更换电池；
- 加速度计；
- 现有 Demo 固件已经实现 EPD 全刷 / 局部刷新、触控跟踪、睡眠与唤醒、TF 存储、AP / STA、本地 HTTP 上传等参考能力。

GR IV 产品能力依据 RICOH 官方 GR IV FAQ、GR IV Operating Manual 与 GR WORLD 说明。

已确认：

- GR IV 支持 Transfer Reservation；
- 支持 Automatic Image Transfer；
- 支持 Auto Resize Transfer；
- 图像传输通过 Wi-Fi；
- 普通连接可使用 Bluetooth；
- GR IV 支持配置 2.4 GHz / 5 GHz Wi-Fi；
- XS JPEG 分辨率已明显高于 Read Pico 最终显示分辨率，适合作为相框同步输入。

未被官方公开资料直接确认的部分，均在本文中标记为 Demo Gate / 待验证，而不是产品既定能力。
