# 当前需求基线：PhotoFrame 移植与 GR 扩展

版本：方案重整 v3，首版范围收敛；日期：2026-10-11。依据是用户确认的“直接基于 aitjcize/esp32-photoframe 移植，先墨水屏功能、后理光 GR 连接”，以及优先交付网页上传、显示与轮播，其他优化移至下一版本的要求。

## 产品与范围

目标设备为小纸 Pico（Read Pico），目标显示为 1216×684、16 灰阶电子纸。当前目标是使 PhotoFrame 的相框业务在该板卡运行。Web 管理是设备内置功能；最终交付为可复现构建且经过实屏验收的固件。

能力边界：4bpp/GC16 的 16 个输入码不等于实屏已能分辨 16 级。历史“白色偏多”已定位为自动DFS下扫描事务缺少CPU/APB PM锁；2026-10-04同机候选恢复官方量级相位时长，单张标准页实拍16阶严格单调并人工确认。固定厂家完整波形头文件声明约11级可分辨不代替本机证据，也不降低16灰目标。该单次通过尚不代表重复性、照片链路和长期稳定验收完成，见 [显示适配](READ-PICO-DISPLAY.md) 和 [验证记录](VALIDATION.md)。

沿用既有全屏要求：照片按比例放大并居中裁切铺满屏幕，不拉伸、不新增纸边，保留原文件。

## 第一阶段：墨水屏相框

第一阶段分期交付：R1先交付可用本地相框，以USB供电、保持在线、不睡眠为首版运行边界，必须具备设备网页访问、上传至SD、选图实屏显示、自动轮播和重启后的文件/必要配置保持。采用现有等比Cover和GC16，不删除原片。基本失败反馈、数据安全和启用路径的可靠性仍是必需项。

R2承接触摸、PMU低功耗、OTA、URL来源完整验证、扩展兼容、缓存/大图性能及长期压力验收；R1不等于完整第一阶段完成。暂不交付的入口须禁用或明确拒绝，不得默默后台运行。进度和具体执行/验收清单只在TODO维护。

复用 PhotoFrame 的相册、Web Gallery/上传、REST、Wi-Fi 配置、图片处理、SD/URL 轮播、电源策略和 OTA 结构；实际能力与接口在 P0 按锁定源码确认。

Read Pico 移植包括板型注册、I2C/IO 扩展/屏幕电源、PMU 状态、只读出厂 VCOM、GC16 显示后端、SDMMC、触摸和外部 PMU 睡眠/唤醒。大型 JPEG 与缓存优化在基本显示闭环之后进行。

交付分为三个层次：

| 交付点 | 必须验证的结果 |
| --- | --- |
| P2 显示基础 | PhotoFrame 4bpp 经适配后正确显示白黑、16 灰阶、像素与方向测试图及照片 |
| P3 相框 MVP | 浏览器上传 → SD → 相册选图/轮播 → 图像处理 → GC16 实屏；重启可再次读取 |
| P5 第一阶段完成 | 触摸、PMU 睡醒、既有产品功能回归、异常恢复与稳定性验收；支持范围和限制可查 |

上游已有能力不等于新板已验证；第一阶段每一项状态必须附本版证据。初始图片格式/大小上限由现有解码器与内存测试确定，不提前承诺完整相机大图或渐进 JPEG 支持。

## 第二阶段：理光 GR 连接

在第一阶段完成后，把相机接入为独立图片来源，依次验证发现/身份/配对、Wi-Fi、只读文件列表与下载，再开发预约同步与功耗策略。日常相机同步以不依赖手机或云端为目标，首期相框仍可使用浏览器管理。

GR IV、GR IV HDF、GR IV Monochrome 为目标兼容范围，须逐型号与固件版本验收。旧协议研究和 BLE 实验只是后续输入，不是现成兼容证明。

相机原片不可删除。未经验证的 BLE 写值、远端 ACK、拍摄或升级操作不得启用。相机副本最终进入 PhotoFrame 的既有存储、处理与显示流程。

## 暂不作为第一阶段要求

旧方案的 NEW/NORMAL 状态机、“留下/放下”、专用决策日志、相机预约通知与 ACK、自动相机同步、相机专用菜单均后置。先根据主工程已有能力再判断是否需要，不照搬旧架构。
